# 비공개 학습 자료함 확장 개발 계획

## 1. 목적과 현재 상태

이 문서는 기존 BuildLog에 자료 파일을 비공개로 보관하는 기능을 추가하는 계획입니다. 요구사항은 [PRD 12절](PRD.md#12-확장-기능-비공개-학습-자료함), 사용자 동작은 [SPEC 15절](spec.md#15-확장-기능-비공개-학습-자료함)을 따릅니다. 기존 MVP Phase 0~13을 바꾸거나 완료 처리하지 않습니다.

현재 M1~M5 코드 구현을 완료했습니다. 임시 SQLite·별도 업로드 폴더를 사용하는 실제 FastAPI/React와 Chrome에서 전체 흐름 및 MP4 재생을 검증했습니다. 실제 Supabase 적용·저장·역할 검증은 아직 하지 않았으므로 확장 기능의 최종 완료 기준 전체를 완료 처리하지 않습니다.

## 2. 확정 범위와 처리 기준

- 작성자 본인의 등록·목록·원본 보기·삭제만 제공합니다. 공개 여부 필드는 만들지 않습니다. 운영자도 이 기능에서 다른 사용자의 자료를 열지 못합니다.
- 제목은 앞뒤 공백 제거 후 1~100자입니다. 단어 사이의 공백은 보존합니다. 메모는 선택이며 최대 1,000자입니다. 제목·메모의 글자 수는 서버의 유니코드 문자 수를 기준으로 하고 프론트도 같은 기준으로 검사합니다.
- 자료당 파일을 정확히 한 개 받습니다. PNG, JPG/JPEG는 각각 최대 5MiB(5,242,880바이트), MP4는 최대 30MiB(31,457,280바이트)입니다. 제한과 같은 크기는 허용하고 1바이트라도 넘으면 거절합니다. 빈 파일은 거절합니다.
- PNG/JPG는 허용 확장자·서버가 확인한 형식이 맞아야 합니다. JPEG의 `.jpg`와 `.jpeg`는 같은 형식으로 취급합니다. 확장자는 대소문자를 구분하지 않습니다. MP4도 확장자만 바꾼 다른 파일을 허용하지 않도록 실제 컨테이너 식별을 검사합니다. 클라이언트의 MIME만 믿지 않습니다.
- 파일은 `backend/uploads` 아래, 메타정보는 Supabase의 새 `materials` 테이블에 저장합니다. Supabase Storage나 Auth는 추가하지 않습니다.
- 목록은 본인 자료만 최신 등록순으로 보여주고, 등록 시간이 같으면 ID 역순으로 정렬합니다. 기존 전체·이미지·영상 필터는 본인 목록을 화면에서 나누는 방식으로 연결합니다.
- 이번에는 수정·검색·다중 파일·공개 공유·댓글·좋아요·AI 분석·썸네일 생성·파일 내용 변환을 만들지 않습니다. 현재 미리보기 그림을 실제 썸네일로 가장하지 않고 파일 종류 표시로 사용합니다.

## 3. 제안 API 계약

M3/M4에서 아래 네 경로를 구현했고 M5에서 프론트와 연결했습니다. 모든 API는 기존 `CurrentUser`를 적용하고, 변경 API는 추가로 `require_csrf`를 적용합니다. 작성자 ID는 요청에서 받지 않고 로그인 사용자에서 정합니다. 실제 Supabase 검증은 별도입니다.

| 메서드·경로 | 요청 | 성공 응답 | 주요 실패 |
| --- | --- | --- | --- |
| `POST /api/materials` | `multipart/form-data`: `title`, 선택 `memo`, `file` 한 개. 쿠키·Origin·X-CSRF-Token 포함 | 201, 저장한 자료의 메타정보 JSON | 401 로그인 필요, 403 CSRF 실패, 413 크기 초과, 415 미지원·위장 형식, 422 입력·파일 개수 오류, 503 DB·저장 실패 |
| `GET /api/materials` | 쿠키 | 200, `{items: [...]}`. 자료 없으면 빈 배열 | 401, 503 |
| `GET /api/materials/{id}/file` | 쿠키, 필요하면 Range 헤더 | 200 원본 바이트, 범위 요청은 206 | 401, 404 미존재·다른 작성자·원본 없음, 400 잘못된 범위 문법, 416 범위 밖 요청, 503 저장소·DB 장애 |
| `DELETE /api/materials/{id}` | 쿠키·Origin·X-CSRF-Token. 본문 없음 | 204, 본문 없음 | 401, 403 CSRF 실패, 404 미존재·다른 작성자, 503 삭제 실패 |

- JSON 항목: `id`, `title`, `memo`(없으면 null), `original_filename`, `media_type`(image/video), `mime_type`, `size_bytes`, `created_at`(시간대 포함 UTC). 화면에서 날짜·용량을 표시합니다.
- 저장용 파일명, 서버 경로, DB 접속 정보는 응답에 넣지 않습니다. 원본 경로는 ID로 조합하며 로그인 필수라는 규칙을 유지합니다.
- `owner_id`까지 조건에 포함해 자료를 찾습니다. 다른 사람의 ID를 바꾸어 요청해도 자료가 있는지 알려주지 않고 404로 응답합니다. GET·DELETE·Range 요청 모두 같은 검사를 합니다.
- 비공개 응답은 `Cache-Control: private, no-store`를 적용합니다. 원본은 검증한 MIME, 안전하게 인코딩한 Content-Disposition, `X-Content-Type-Options: nosniff`를 사용합니다. 파일명은 헤더에 직접 이어 붙이지 않습니다.
- 원본 보기는 쿠키를 포함하는 요청으로 처리합니다. GET이므로 CSRF 헤더를 붙이지 않아도 되지만 인증은 반드시 검사합니다. 공개 정적 URL을 만들지 않습니다.
- MP4 원본 보기에는 서버의 FileResponse 범위 응답과 브라우저 재생을 확인합니다. 프론트와 API의 출처가 다르면 원본 주소 구성·쿠키 동작·CORS의 Range 요청도 함께 검증합니다. 연결 URL에 토큰을 넣지 않습니다.
- 오류 응답은 기존 `{detail: "안내 문구"}` 형태를 따릅니다. DELETE 204를 JSON으로 읽어 성공을 실패로 바꾸지 않도록 프론트 응답 처리를 분리합니다.

## 4. 테이블과 로컬 파일 설계안

### materials 테이블

| 컬럼 | 제안 형식·조건 | 용도 |
| --- | --- | --- |
| id | Integer 기본키 | 기존 users ID 방식에 맞춤 |
| owner_id | Integer, users.id 외래키, 필수 | 로그인 작성자. 다른 작성자 자료 접근 차단 |
| title | String(100), 필수, 길이·앞뒤 공백 검사 | 제목 |
| memo | String(1000), null 허용, 최대 길이 검사 | 선택 메모. 빈 문자열은 null로 통일 |
| original_filename | Text, 필수 | 경로를 제거한 원래 파일명 표시용. 저장 경로로 사용하지 않음 |
| stored_filename | String(255), 필수·고유 | 서버가 생성한 UUID 기반 파일명과 검증한 확장자 |
| media_type | String(5), image/video CHECK | 필터 분류 |
| mime_type | String(32), 허용 MIME CHECK | image/png, image/jpeg, video/mp4 |
| size_bytes | BigInteger, 양수·형식별 최대 크기 CHECK | 실제 읽은 파일 크기 |
| created_at | DateTime(timezone=True), 필수·서버 UTC 기본값 | 등록일 |

- 형식과 MIME 조합, 크기 제한을 모델·DB 제약에 함께 반영합니다. `(owner_id, created_at, id)` 조회 인덱스를 둡니다.
- users 테이블과 기존 마이그레이션은 수정하지 않습니다. 후속 revision은 기존 실제 head를 확인해 연결합니다. 계정 삭제 기능은 없으므로 파일 정리 없는 외래키 cascade 삭제를 임의로 추가하지 않습니다.
- DB 직접 접근 경로가 비공개 자료를 노출하지 않게 materials의 Supabase Data API 노출·권한을 검증합니다. RLS를 사용한다면 기존 FastAPI DB 접속 역할을 확인하고 anon/authenticated 직접 접근은 차단합니다. Supabase Auth의 `auth.uid()`에 기존 쿠키 로그인이 연동된다고 가정하지 않습니다.

### 저장 디렉터리

- 프로젝트 위치 기준 절대 경로로 `backend/uploads`를 계산합니다. 실행 터미널 위치에 따라 저장 장소가 달라지지 않아야 합니다.
- 예시 구조는 `backend/uploads/{owner_id}/{uuid}.{검증한 확장자}`입니다. 업로드 임시 파일도 이 루트의 별도 내부 폴더를 사용합니다. 사용자가 보낸 경로나 파일명으로 저장 경로를 정하지 않습니다.
- 최종 경로를 정규화하고 uploads 내부인지 검사합니다. 같은 이름의 원본 파일도 새 저장용 이름으로 보관해 덮어쓰지 않습니다. 심볼릭 링크를 이용한 루트 밖 접근도 차단합니다.
- `uploads`를 StaticFiles로 공개하거나 프론트 public 폴더에 복사하지 않습니다. 파일을 여는 유일한 경로는 작성자 검사를 거친 API입니다.
- 디렉터리는 업로드 구현 시 준비하고 쓰기 권한을 검사합니다. 실제 자료·임시 파일은 Git에서 제외하며 검증용 파일은 별도 테스트 디렉터리를 씁니다.

### DB와 파일의 실패 처리

DB 트랜잭션과 파일 시스템은 한 번에 같이 커밋되지 않습니다. 다음 보상 처리를 구현하고 실패를 테스트합니다.

1. 업로드는 임시 파일에 청크 단위로 기록하며 실제 누적 바이트 수로 제한을 검사합니다. 전체 파일을 한 번에 메모리에 올리지 않습니다. 거절·취소·연결 종료 시 열린 파일과 임시 파일을 정리합니다. Content-Length는 참고만 하며 누락·위조된 경우에도 제한합니다.
2. 형식 검사 후 트랜잭션 안에서 메타정보를 준비하고 고유한 최종 경로로 옮긴 뒤 DB를 커밋합니다. 파일 이동 또는 DB 커밋 실패 시 롤백하고 이번 요청이 만든 파일만 정리합니다. 두 저장이 모두 성공한 경우만 201을 반환합니다.
3. 삭제는 먼저 본인 행을 잠그거나 동등한 방법으로 동시 삭제를 제어합니다. 파일을 내부 임시 보관 위치로 옮기고 DB 행 삭제를 커밋합니다. 커밋 실패 시 파일을 원위치로 복구합니다. 파일 이동 실패 시 행을 보존하고 실패를 반환합니다.
4. DB 삭제 커밋 후 임시 보관 파일을 제거합니다. 정리가 실패한 경우는 남은 내부 파일로 기록하고 재정리하며, DB는 삭제됐는데 화면에 ‘삭제 실패’만 표시하는 모순을 피합니다. 정리 기록에는 비밀값·파일 내용·사용자의 메모를 남기지 않습니다.
5. DB 행은 있지만 원본만 이미 없는 경우 원본 보기는 404이며, 본인 삭제는 행을 정리할 수 있게 합니다. 프로세스가 중간에 종료되면 파일이 남을 수 있으므로 uploads와 DB를 대조하는 복구 절차를 실행 안내에 남깁니다. 자동 복구 서비스는 이번 범위가 아닙니다.

## 5. 개발 순서와 단계별 산출물

각 단계는 별도 작업으로 수행하고 결과를 보고합니다. 이전 단계 완료만으로 뒤 단계까지 구현했다고 표시하지 않습니다.

### M1. 파일 선택

**작업**

1. `/materials` 기존 디자인·라우팅·전용 CSS와 홈 링크를 유지합니다.
2. 제목·메모·선택 파일을 React 상태로 관리합니다. 제목 trim 및 글자 수, 메모 길이를 검사합니다. HTML maxLength만으로 서버와 문자 수가 같다고 가정하지 않습니다.
3. 실제 파일 input을 파일 선택 버튼에 연결합니다. `multiple`은 사용하지 않고 accept는 PNG/JPEG/MP4로 제한합니다. accept는 보안 검사가 아니며 서버 재검사는 M3에서 합니다.
4. 선택한 파일명·종류·바이트 수를 표시하고 종류별 MiB 한도를 검사합니다. 파일을 바꾸거나 선택 대화상자를 취소할 때 상태가 잘못 사라지지 않게 합니다. 제한 초과·잘못된 파일에는 쉬운 안내를 표시합니다.
5. 아직 서버는 호출하지 않습니다. 업로드 버튼은 M5까지 연결 예정 상태이며 저장 성공을 표시하지 않습니다. 예시 목록과 실제 선택 파일을 저장된 자료처럼 섞지 않습니다.

**예정 산출물**: 기존 MaterialsPage와 필요할 때만 전용 CSS 변경, 자료 입력 검증 모듈, 프론트 테스트.

**완료 확인**: 제목 0/1/100/101자, 앞뒤 공백·내부 공백, 메모 0/1000/1001자, 한글·이모지 문자 수, 이미지·영상의 제한값과 +1바이트, 재선택·취소, 서버 요청 0건. 360px 표시 유지.

### M2. 테이블 준비

**작업**

1. materials SQLAlchemy 모델과 DB 제약·외래키·인덱스를 추가합니다. 기존 users를 바꾸지 않습니다.
2. Alembic env에 새 모델 메타정보를 등록하고 기존 head 다음에 새 revision을 추가합니다.
3. 별도 임시 SQLite에서 구조·제약·up/down/up 및 두 번 upgrade의 재적용 없음, PostgreSQL용 SQL 생성을 검사합니다. downgrade 검사는 테스트 DB에서만 하며 사용자 DB를 되돌리지 않습니다.

## 7. 실행 준비와 운영상 한계

- 사용자가 새 비밀값을 제공할 필요는 없습니다. 기존 `backend/.env`의 Supabase 연결과 쿠키 설정을 사용합니다. 내용은 문서·답변에 출력하지 않습니다.
- 구현 시 backend/uploads 쓰기 권한과 충분한 디스크 공간, 서버 재시작·재배포 뒤 파일이 유지되는 저장 공간을 확인해야 합니다. DB만 Supabase에 있으므로 서버 파일이 사라지면 원본을 복원할 수 없습니다. 백업은 DB 메타정보와 uploads를 함께 보관해야 합니다.
- 이번 범위는 단일 백엔드와 로컬 디스크 저장 기준입니다. 여러 서버 간 파일 공유, 총 사용량 제한, 악성 파일 정밀 검사 서비스, 저장소 이전, 자동 복구·정리 작업은 미포함입니다. 파일 헤더·컨테이너 검사만으로 모든 코덱의 재생 또는 모든 파일의 안전성을 보장한다고 표시하지 않습니다.
- M3에서 결정: 이미지 검사는 Pillow 13.0.0, multipart는 python-multipart 0.0.32, MP4는 제한된 크기의 ISO-BMFF 박스·브랜드·영상 트랙 검사입니다. 전체 요청은 multipart 오버헤드 포함 최대 32MiB, 수신 시간은 120초, 파일은 64KiB 청크로 복사합니다. 파일별 5/30MiB 제한은 별도로 검사합니다.
- 아직 미정: 실제 배포 환경의 영구 디스크·백업 위치. 서버/배포 환경 정보가 필요한 시점에 별도로 확인합니다.
- 다음 확인은 실제 Supabase의 마이그레이션 적용 상태·권한과 실제 사용자 환경에서의 저장 흐름입니다. 코드 M1~M5는 완료했으며, DB 준비가 안 되면 현재 화면은 오류를 안내하고 예시로 대체하지 않습니다.

### M3 업로드 API 완료 (2026-10-24)

- `POST /api/materials`를 구현했습니다. 기존 CurrentUser·DatabaseSession·require_csrf를 사용하고, multipart에서 제목·선택 메모·파일 한 개만 받습니다. 작성자 ID 등 추가 필드, 중복 필드와 다른 이름의 추가 파일도 거절합니다.
- 요청 MIME은 multipart만 허용하며 Content-Length와 무관하게 실제 수신 바이트를 32MiB로 제한합니다. 수신 120초 초과는 408, 크기 초과는 413, 미지원/위장 형식은 415, 입력 오류는 422, 저장 장애는 503입니다. 인증 실패 401·CSRF/Origin 실패 403을 유지합니다.
- Pillow로 PNG/JPEG 구조와 디코딩을 검사하고 원본은 재작성하지 않습니다. MP4는 파일명만 믿지 않고 컨테이너 브랜드·박스 경계·mdat·영상 트랙을 검사합니다. 전체 코덱의 재생이나 모든 미디어 내용의 무해함을 보장하는 검사는 아닙니다.
- 파일은 backend/uploads/.tmp에서 검증한 후 작성자 폴더의 UUID 이름으로 저장합니다. 원래 이름의 경로/제어문자를 제거·거절하며 기존 파일을 덮어쓰지 않습니다. 경로 정규화와 심볼릭 링크/Windows junction 검사를 합니다. 공개 정적 경로는 만들지 않습니다.
- multipart 파서 자체의 임시 파일은 Starlette의 비공개 시스템 임시 저장소를 사용하며 정상/실패/연결 종료 시 닫습니다. 앱이 관리하는 준비·최종 파일은 uploads 아래에 둡니다. 실제 데이터는 테스트에 사용하지 않았습니다.
- DB flush→안전 응답 검증→파일 게시→DB commit 순서이며 실패·취소 시 롤백하고 이번 요청의 준비/게시 파일만 제거합니다. 커밋 시작 뒤 클라이언트가 떠난 경우 작업은 커밋 또는 보상 정리를 마칠 때까지 진행하므로 응답 유실 후 자동 재전송은 금지합니다. 강제 프로세스 종료·네트워크 단절로 커밋 결과가 불확실한 경우에는 기존 계획의 파일/DB 대조가 필요합니다.
- python-multipart 0.0.32·Pillow 13.0.0을 설치하고 고정했습니다. uploads와 내부 임시 폴더를 준비했고 Git 제외를 확인했습니다. 실제 환경 변수나 DB 접속 설정은 바꾸지 않았습니다.
- 검증: 임시 SQLite·임시 uploads에서 정상 PNG/JPEG·MP4 컨테이너 등록, 정확한 크기 한도, 잘못된 형식·크기·입력, 로그인·CSRF·작성자 지정, 중복 파일명, 부분 쓰기/게시/DB 커밋 실패, 취소·수신 종료 시 정리를 검사했습니다. 실제 심볼릭 링크 생성 테스트는 Windows 권한으로 건너뛰었고, 링크 감지 분기의 거절은 별도 모의 테스트로 확인했습니다.
- 최종 결과: 백엔드 테스트 166개 통과·1개 건너뜀, pip check 통과. 실제 uploads에는 자료 파일이 없으며 Git 제외를 확인했습니다. 프론트 변경이 없어 프론트 테스트·빌드는 반복하지 않았습니다.
- 미확인: 실제 Supabase 적용/저장/권한, 실제 재생 가능한 MP4와 브라우저 동작, 디스크 고장/정리 자체 실패 및 프로세스 강제 종료 복구. 프론트 업로드·조회·삭제·AI는 연결하지 않았습니다. 다음은 M4이며 commit·push는 하지 않았습니다.

### M4 목록·원본 보기·삭제 API 완료 (2026-10-24)

- GET /api/materials는 본인 자료의 안전한 메타정보만 최신 등록일·ID 역순으로 응답합니다. 빈 목록은 `{items: []}`입니다. SQLite 테스트에서 사라지는 시간대 정보도 UTC로 표시하도록 응답 직렬화를 통일했습니다.
- GET /api/materials/{id}/file는 작성자 확인 후 안전한 저장 경로의 원본을 열어 PNG/JPEG/MP4 MIME과 인코딩한 원래 파일명으로 응답합니다. 열린 파일 핸들을 사용하므로 응답 직전에 경로를 다시 열지 않습니다. 전체·단일/여러 범위·If-Range 응답 및 종료 시 핸들 정리를 구현했습니다.
- DELETE /api/materials/{id}는 기존 CSRF/Origin 검사와 작성자 조건을 사용합니다. PostgreSQL에서는 행 잠금을 요청하고, 파일을 .trash로 옮긴 뒤 DB 삭제를 커밋합니다. 커밋 실패·취소 시 행 롤백과 원본 복원을 시도합니다.
- 원본이 이미 없으면 본인 행을 삭제할 수 있습니다. 정상 삭제는 204 본문 없음, 재삭제는 404입니다. 커밋 후 .trash 제거만 실패하면 204를 유지하고 내부 정리 필요 로그를 남깁니다. 복구 자체도 실패하면 파일을 .trash에 보존하고 503 및 비밀값 없는 로그로 처리합니다. 실제 디스크 고장·커밋 결과 불확실/강제 종료는 수동 복구 대상입니다.
- `.trash/{임시UUID}-{저장용파일명}` 이름으로 남은 파일을 메타정보와 대조할 수 있습니다. .trash도 Git 제외 및 비공개입니다. 복구 시 파일 내용·작성자와 DB 상태를 확인하고 기존 원본을 덮어쓰지 않습니다.
- 다른 작성자와 없는 ID는 같은 404입니다. 운영자도 다른 사람 자료를 볼 수 없습니다. 비로그인은 목록·원본·범위·삭제 모두 401입니다. materials 응답에는 private/no-store와 nosniff를 적용하고 CORS에 범위 요청·원본 관련 응답 헤더를 추가했습니다. 공개 정적 경로는 없습니다.
- 검증: 백엔드 전체 테스트 193개 통과·1개 건너뜀. 임시 SQLite·임시 uploads에서 본인 목록/정렬/빈 목록, 두 사용자 분리(운영자 포함), 원본 바이트·MIME·파일명, Range/If-Range/오류·CORS, 삭제·재삭제·원본 없음, 이동/커밋/복구/최종 정리 실패·취소, 잘못된 DB 경로·링크 감지 거절을 검사했습니다. 건너뛴 항목은 M3의 Windows 실제 심볼릭 링크 생성입니다.
- 미확인: 실제 Supabase 적용/역할/동시 행 잠금, 실제 브라우저의 MP4 재생 및 화면 연결. 프론트·환경 변수·회원/마이그레이션 파일은 변경하지 않았습니다. 다음은 M5이며 commit·push는 하지 않았습니다.

### M5 화면 연결 완료 (2026-10-24)

- 자료 전용 API 모듈을 추가했습니다. FormData의 Content-Type은 브라우저가 정하며 쿠키와 기존 CSRF를 보냅니다. JSON 인증 클라이언트는 API 기본 주소 export만 추가했고 기존 요청 동작은 유지했습니다. AuthProvider에 기존 mutate 재사용과 세션 갱신 함수를 노출했습니다.
- 예시 배열을 제거하고 실제 본인 목록·전체/이미지/영상 필터·개수·메모·파일 정보·날짜를 표시합니다. 로딩·빈 목록·조회 실패·재시도와 이전 목록을 구분합니다. 목록을 확인하지 못했으면 업로드/원본/삭제를 제한하고 먼저 다시 조회하도록 합니다.
- 유효한 제목·메모·선택 파일이 있으면 업로드할 수 있습니다. 처리 중 입력·버튼과 중복 요청을 막고, 201 후에만 입력을 비우고 목록에 반영합니다. 실패하면 입력/선택 파일/기존 목록을 유지합니다. 시간 초과나 불확실한 응답은 목록 재확인을 안내하며 자동 재전송하지 않습니다.
- 업로드 대기는 180초, 일반 목록/삭제는 15초, 원본은 120초입니다. 페이지를 떠나면 해당 페이지의 요청을 중단합니다. 클라이언트 중단이 서버 커밋 취소를 보장하지 않으므로 복귀 시 서버 목록을 다시 읽습니다.
- 원본은 쿠키를 포함한 fetch 후 MIME·크기를 확인하고 Blob URL로 같은 화면에 표시합니다. 이미지·영상은 자동 재생하지 않으며 닫기/교체/삭제/화면 이탈 시 URL을 해제합니다. 브라우저가 표시하지 못하면 원본 내려받기를 안내합니다. 생성한 썸네일이나 예시 영상을 실제 자료처럼 사용하지 않습니다.
- 삭제 확인 후 204일 때만 카드·개수·열린 원본을 제거합니다. 취소/실패 시 카드를 유지하고 404면 현재 목록을 재조회합니다. 401/403은 기존 세션 갱신을 사용하되 변경 요청은 재실행하지 않습니다. 로그인 사용자가 바뀌면 페이지 상태도 초기화합니다. AI는 비활성 연결 예정입니다.
- 서버와 제목 정규화 기준을 맞추기 위해 Python str.strip의 유니코드 공백 범위를 프론트에 적용했습니다. 제목 내부 공백과 선택 메모 원문은 유지합니다.
- 자동 검증: 프론트 테스트 80개·빌드 통과. 기존 로그인·대시보드 회귀, 입력/파일 제한, 목록 오류/재시도/필터, 업로드 성공/실패/중복 제출/타임아웃, CSRF 갱신·인증 만료, 삭제 확인/실패/404/성공, Blob 정리와 요청 중단을 확인했습니다.
- 실제 브라우저 검증: 프로젝트 환경 파일과 운영 서버를 사용하지 않고 임시 디렉터리에 별도 SQLite·uploads·백엔드(18001)와 프론트(5174)를 띄웠습니다. 모의 API가 아닌 실제 React→FastAPI→임시 DB/파일 저장으로 가입→로그인→PNG 등록→원본 이미지 표시→새로고침 유지→삭제를 확인했습니다. Chrome 캔버스로 생성한 실제 MP4도 등록·디코딩·재생했고, 1440px/360px 가로 넘침 없음, 삭제 후 빈 목록/새로고침을 확인했습니다. 확인용 서버/브라우저는 종료하고 기존 서버는 유지했습니다.
- 미확인: 실제 Supabase 적용/저장/RLS/동시성, Edge·Safari·실제 휴대폰, 여러 MP4 코덱과 배포 환경의 영구 디스크. 실제 사용자 데이터·backend/.env·백엔드 실행 코드·마이그레이션은 변경하지 않았습니다. commit·push는 하지 않았습니다.
