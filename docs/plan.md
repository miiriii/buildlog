# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 해당 단계의 자동 테스트와 직접 확인을 수행합니다. 화면이 있는 단계는 브라우저 확인도 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. 서버에서도 사용 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite3 데이터 파일과 부속 파일, `.env`, `.venv`, `node_modules`, `dist`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다. `.env.example`은 비밀값 없이 기록할 수 있게 합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- 프론트엔드는 React, 백엔드는 FastAPI로 분리합니다. React는 API로 FastAPI와 통신하며 DB에 직접 연결하지 않습니다.
- 운영·로컬 실행 DB는 Supabase의 PostgreSQL Session pooler를 사용하고, 자동 테스트는 별도 임시 SQLite3를 사용합니다. `backend/.env`에 연결 정보가 없으면 실행을 중단하며 SQLite3로 대체하지 않습니다. 아래 Phase 0~3의 SQLite3 수행 결과는 당시의 이력입니다.
- React 개발 도구는 Vite, DB 접근은 SQLAlchemy, DB 구조 변경 관리는 Alembic을 사용할 계획입니다. 필요한 최소 패키지만 사용하며 호환 버전은 Phase 0에서 확인합니다.
- Supabase는 DB 역할로 사용합니다. Supabase Auth, Storage 등 다른 기능은 임의로 추가하지 않습니다. 회원과 로그인은 FastAPI에서 처리하며 인증의 세부 방식은 Phase 0에서 정리합니다.
- 서버의 비밀값과 DB 연결 정보는 백엔드 환경 변수에만 둡니다. React에 전달되는 환경 변수에는 공개 가능한 API 주소만 넣습니다.
- 화면이 포함된 각 기능 Phase에서는 FastAPI 입력·응답 스키마, API 처리, 서버 권한 검사, React API 요청·화면·상태 처리를 함께 연결합니다. 서버 검사는 React 검사와 독립적으로 동작해야 합니다.
- 백엔드 자동 테스트는 pytest와 FastAPI 테스트 클라이언트, React 화면 테스트는 Vitest와 React Testing Library를 사용할 계획입니다. 공통 테스트 설정은 필요 단계에서 준비하고, 백엔드와 프론트엔드 테스트를 별도로 실행합니다.
- SQLite3와 PostgreSQL에서 같은 데이터 규칙을 지키도록 설계합니다. SQLite3 검증과 Supabase 검증의 결과를 구분하고, Supabase 검증을 마치기 전에는 운영 DB 준비 완료로 표시하지 않습니다.
- 기존 `docs/README.md`의 내용은 유지합니다. 설치·실행 설명은 `docs/setup.md`에 작성합니다.

## 3. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ requirements.txt
│  ├─ .env.example      # 백엔드 설정 항목. 실제 값은 Git 제외된 .env
│  ├─ app/
│  │  ├─ main.py       # FastAPI 시작점과 라우터 연결
│  │  ├─ core/         # 환경 설정, 인증과 공통 권한
│  │  ├─ db/           # SQLAlchemy 연결, 세션과 공통 모델 기반
│  │  ├─ accounts/     # 회원 모델, 입력·응답 형식, API와 처리 로직
│  │  ├─ records/      # 공부 기록·할 일·오류 기록 모델과 API
│  │  └─ community/    # 댓글·좋아요·신고 모델과 API
│  ├─ migrations/      # Alembic DB 구조 변경 이력
│  ├─ alembic.ini
│  └─ tests/           # 분리된 테스트 DB를 사용하는 자동 테스트
├─ frontend/
│  ├─ package.json
│  ├─ package-lock.json
│  ├─ index.html
│  ├─ vite.config.js
│  └─ src/
│     ├─ main.jsx
│     ├─ App.jsx
│     ├─ api/          # FastAPI 요청과 공통 응답 처리
│     ├─ components/   # 공통 메뉴, 입력칸, 카드 등
│     ├─ pages/        # 회원·기록·공개·운영자 화면
│     ├─ styles/       # 공통 CSS
│     └─ tests/        # 화면 동작 테스트
├─ database/
│  └─ buildlog.sqlite3 # 기존 데이터 보존용, Git 제외. 자동 테스트 DB는 별도 사용
├─ .env.example        # backend/.env.example 위치 안내
└─ docs/               # 요구사항, 동작 설명서, 개발 문서. Supabase DB는 원격에 위치
```

## 5. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위가 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. Python, Node.js와 npm의 설치 여부를 읽기 전용 명령으로 확인하고 React·Vite·FastAPI·SQLAlchemy·Alembic의 호환되는 안정 버전을 확인합니다.
4. Python에서 SQLite3를 사용할 수 있는지 확인합니다. Supabase의 PostgreSQL과 다른 제약 조건, 날짜·시간, 검색 동작과 DB 구조 변경 방법도 검토합니다.
5. 개발용 주소는 React `http://localhost:5173`, FastAPI `http://localhost:8000`, 로컬 DB 파일은 `database/buildlog.sqlite3`를 기준으로 정리합니다. 주소 충돌 여부와 API 주소·허용 출처(CORS) 설정을 확인합니다.
6. 백엔드의 `DATABASE_URL`, `SECRET_KEY`, `CORS_ORIGINS`, 프론트엔드의 `VITE_API_BASE_URL` 항목과 인증 방식·로그인 상태 유지 방법을 정리합니다. 실제 비밀값은 문서에 적지 않습니다.
7. 백엔드 API 테스트와 React 화면 테스트 도구, 빌드·실행 명령을 문서에 기록할 준비를 합니다.
8. Supabase 연결 정보는 로컬 개발 시작에 필수로 요구하지 않습니다. Supabase 검증에 필요한 별도 검증 환경과 연결 방식, 준비 시점을 정리합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 실행 환경을 설명할 `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위가 충돌하지 않는지 확인합니다.
- Python, Node.js, npm 실행 여부와 버전, SQLite3 사용 가능 여부를 읽기 전용 명령으로 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 완료 조건

- 로컬 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다. 미해결 문서 충돌은 사용자에게 확인합니다.
- Supabase 연결 정보가 아직 없으면 연결 검증 대기 상태로 기록하며, 해당 검증을 완료한 것으로 표시하지 않습니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

#### 수행 결과 — 2026-10-22

- 상태: Phase 0 완료. Phase 1은 아직 시작하지 않았습니다.
- 문서 범위와 제외 기능을 확인했습니다. 오류 초기 상태의 상충 문구는 사용자의 답변에 따라 “기본 미해결, 해결 방법을 입력하고 해결을 선택하면 최초 해결 저장 가능”으로 정리했습니다.
- Python 3.14.6과 SQLite3 라이브러리 3.53.1, Node.js 24.22.0, npm 11.19.1 실행을 확인했습니다. 전역 기본 Python 3.15.0은 변경하지 않습니다.
- 프로젝트 Python 선택 명령은 `py -V:Astral/CPython3.14.6`입니다. `venv`·pip 사용이 가능하여 추가 Python·Node.js 설치가 필요하지 않습니다.
- FastAPI·React·Vite·SQLAlchemy·Alembic 및 테스트 도구의 안정 배포 메타데이터와 요구조건을 확인했습니다. 실제 설치·통합 실행 검증은 아직 하지 않았습니다.
- 점검 시점에 개발 포트 5173·8000을 사용하는 수신 프로세스는 없었습니다.
- 환경 변수, 서명된 HttpOnly 쿠키 인증, 비밀번호 해시, CORS·CSRF 처리 기준, SQLite3·PostgreSQL 차이와 실행·테스트 명령을 [setup.md](setup.md)에 기록했습니다.
- Supabase 프로젝트와 연결 정보는 아직 없으며 연결 검증은 Phase 13 대기입니다. 로컬 개발 시작을 막는 항목은 아닙니다.
- 패키지 설치, 가상환경·기능 코드·DB 생성, Git 초기화·커밋을 하지 않았습니다. README.md와 .gitignore는 유지했습니다.

### Phase 1. FastAPI·React 프로젝트 뼈대 만들기

#### 목표

FastAPI와 React 개발 서버를 각각 실행하고 React 기본 화면에서 FastAPI 상태 확인 API를 호출할 수 있게 합니다.

#### 작업

1. `backend/.venv`에 Python 가상환경을 준비합니다.
2. FastAPI와 실행 서버 Uvicorn, 설정·테스트에 필요한 최소 패키지를 설치하고 버전을 `backend/requirements.txt`에 기록합니다.
3. `backend/app/main.py`와 공통 환경 설정을 만듭니다.
4. `frontend`에 Vite 기반 React 프로젝트를 만들고 npm 잠금 파일로 의존 버전을 기록합니다.
5. API 요청 모듈, 기본 React 화면과 공통 CSS를 만듭니다.
6. DB 연결 항목의 로컬 기본값은 SQLite3 파일을 가리키도록 준비하되 아직 DB를 생성하거나 마이그레이션하지 않습니다.
7. `.env.example`에 백엔드 설정 항목을, `frontend/.env.example`에 공개 가능한 API 주소 항목을 기록합니다. 실제 `.env`의 비밀값은 기록하지 않습니다.
8. 프론트엔드 주소를 FastAPI의 허용 출처로 설정하고 API 주소를 연결합니다. 인증 방식에 맞는 쿠키·요청 설정도 준비합니다.
9. SQLite3 파일과 부속 파일, `.env`, `.venv`, `node_modules`, `dist` 등 생성 파일을 `.gitignore`에 보완합니다. 두 `.env.example`은 기록 가능하게 유지합니다.
10. 상태 확인 API와 React 기본 화면을 연결합니다. 이 단계에서는 회원·기록 기능을 만들지 않습니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/app/main.py`
- `backend/app/core/config.py`
- `backend/tests/test_health.py`
- `frontend/package.json`, `frontend/package-lock.json`, `frontend/vite.config.js`, `frontend/index.html`
- `frontend/src/main.jsx`, `frontend/src/App.jsx`
- `frontend/src/api/client.js`
- `frontend/src/pages/HomePage.jsx`
- `frontend/src/styles/base.css`
- `frontend/src/tests/`
- `frontend/.env.example`
- `.env.example`
- `.gitignore`

#### 확인 방법

- 두 개발 서버가 오류 없이 시작되는지 확인합니다.
- 상태 확인 API 자동 테스트와 React 기본 화면 테스트·빌드를 확인합니다.
- 브라우저에서 React 화면과 CSS가 보이고 FastAPI 상태 확인 결과가 표시되는지 확인합니다.
- 프론트엔드와 백엔드의 주소 설정 및 허용 출처 처리를 확인합니다.
- 비밀 설정값과 SQLite3 파일이 기록 대상에서 제외되는지 규칙으로 확인합니다. 이를 위해 Git 초기화는 하지 않습니다.

#### 완료 조건

- 두 서버와 기본 화면, API 통신이 정상 실행되어야 합니다.
- 아직 DB 생성이나 마이그레이션을 하지 않습니다. 첫 DB 구조는 Phase 2에서 만듭니다.

#### 수행 결과 — 2026-10-22

- 상태: Phase 1 완료. 다음 작업은 Phase 2이며 아직 시작하지 않았습니다.
- `backend/.venv`에 Python 3.14.6 환경을 만들고 FastAPI·Uvicorn·설정·테스트 패키지를 설치했습니다. 전이 의존성을 포함한 실제 버전을 `backend/requirements.txt`에 고정했습니다.
- Vite 기반 React와 공통 CSS, 상태 확인 화면, API 요청 모듈을 만들고 `frontend/package-lock.json`을 생성했습니다.
- `/api/health`는 공개 상태만 응답합니다. React는 쿠키를 포함하는 요청으로 연결을 확인하며, 실패 시 다시 확인할 수 있습니다.

### Phase 2. 사용자 모델과 첫 데이터베이스 만들기

#### 작업

1. `backend/app/accounts`와 공통 DB 연결 모듈을 만듭니다.
2. SQLAlchemy로 사용자 모델을 만들고 SQLite3·PostgreSQL에 공통으로 적용할 구조를 정합니다.
3. 이메일은 필수이며 중복되지 않게 합니다.
4. 닉네임은 필수이며 중복되지 않게 합니다.
5. 닉네임은 2~20자이고 한글, 영문, 숫자, 밑줄만 허용합니다.

8. SQLAlchemy 메타데이터와 Alembic을 연결하고 사용자 모델의 첫 마이그레이션을 만듭니다.
9. 빈 로컬 SQLite3 DB에 마이그레이션을 적용합니다. 테스트는 별도 DB로 실행하고 각 연결에서 외래키 제약이 적용되는지 확인합니다.

### Phase 4. 공부 기록·할 일·오류 기록의 데이터 구조

#### 목표

화면 작업 전에 세 가지 기록이 안전하게 저장될 공통 기반을 만듭니다.

#### 작업

1. `backend/app/records` 모듈을 만듭니다.
2. 공부 기록 모델을 만듭니다.
   - 작성자, 제목, 내용, 공개 여부
   - 작성 날짜·시간, 수정 날짜·시간
3. 할 일 모델을 만듭니다.
   - 작성자, 제목, 완료 여부, 공개 여부
   - 작성 날짜·시간, 수정 날짜·시간, 완료 날짜·시간
4. 오류 기록 모델을 만듭니다.
   - 작성자, 오류 제목, 오류 내용, 해결 방법, 해결 여부, 공개 여부
   - 작성 날짜·시간, 수정 날짜·시간, 해결 날짜·시간
5. 새 기록은 기본 비공개로 설정합니다.
6. 새 할 일의 기본값은 미완료, 새 오류의 기본값은 미해결로 설정합니다. 오류는 해결 방법을 입력하고 해결 상태를 선택하면 처음부터 해결로 저장할 수 있게 준비합니다.
7. 제목과 내용의 최대 길이를 입력 스키마와 데이터 저장 처리 양쪽에서 검사할 수 있게 준비합니다.
8. 기록 작성자와 사용자 모델을 연결합니다.

| 항목 | 로컬 개발·테스트 | Supabase 연결 검증 시 |
| --- | --- | --- |
| 프론트엔드 | React 개발 서버, 기본 주소 `http://localhost:5173` | 같은 React 코드에서 FastAPI 주소를 설정 |

| DB | 실행은 Supabase PostgreSQL, 자동 테스트는 별도 임시 SQLite3 DB | 운영 데이터와 분리한 Supabase 검증용 DB |
| DB 연결 설정 | `backend/.env`의 `DATABASE_URL`에 Session pooler PostgreSQL 연결 설정 | 같은 방식으로 검증용 DB의 연결 정보 입력 |

| API 통신 | `VITE_API_BASE_URL`과 백엔드 `CORS_ORIGINS`를 개발 주소에 맞춤 | 실행 주소에 맞춤. 비밀값을 `VITE_` 변수에 넣지 않음 |

- DB 비밀번호나 전체 연결 문자열을 채팅이나 문서에 붙여 넣지 않습니다. 필요한 시점에 사용자가 백엔드 로컬 환경 파일에 입력할 수 있게 안내합니다.

## 28. 현재 로컬 작업 Git 저장 준비 (2026-11-08)

- 사용자의 현재 로컬 내용 commit/push 요청에 따라 변경 내역과 main/origin 연결, 기존 작성자 설정을 확인했습니다. 회원·자료함·AI 백엔드와 테스트/마이그레이션, 프론트 파일, debug-practice, 문서·작업 규칙·비밀값 없는 예제 설정을 저장 대상으로 확인했습니다.
- 현재 frontend의 진입 화면·package 설정은 오류 실습용으로 바뀌어 있으며 미정의 변수 참조를 잡아 표시하는 실습 코드가 있습니다. debug-practice의 빈 프론트 파일과 별도 백엔드도 현재 상태 그대로 보존하며 임의 복원·기능 수정은 하지 않았습니다.
- 확인: 백엔드 테스트 232개 통과·1개 건너뜀, 현재 실습 프론트 빌드 통과. 과거 BuildLog 화면 전체의 현재 동작이나 EC2 배포 성공을 검증한 것은 아닙니다.
- Git 후보 파일을 실제 로컬 비밀 설정값 및 자격 증명 형태와 대조해 비밀값이 포함되지 않음을 확인했습니다. 비밀번호가 없는 SQLite 테스트 경로는 인증정보와 구분했습니다. 실제 .env, 가상환경/node_modules, 생성 결과, SQLite 파일, 로그, 업로드 파일은 제외합니다.
- 다음 확인: 관련 변경을 커밋하고 origin/main으로 push한 뒤 로컬 HEAD와 원격 커밋의 일치 여부 및 작업 폴더 상태를 확인합니다. 최종 커밋 번호와 push 결과는 작업 완료 보고에 남깁니다. EC2에서 새 코드를 쓰려면 해당 저장소를 별도로 갱신해야 합니다.
