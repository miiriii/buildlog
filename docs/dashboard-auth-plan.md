# 대시보드 로그인 닉네임 연동 계획

작성일: 2026-10-23. 아래는 당시의 개발 계획입니다. 2026-10-24 구현과 자동 테스트·모의 API 브라우저 검증을 마쳤으며, 결과는 [SDD 11장](dashboard-auth-sdd.md#11-구현검증-결과-2026-10-24)에 기록했습니다. 실제 Supabase 계정 연동 확인은 미수행입니다.

## 1. 목표와 범위

`/dashboard`의 인사말, 왼쪽 계정명과 아바타 첫 글자를 실제 로그인한 사용자의 닉네임으로 표시합니다. 기존 로그인 정보를 공유하고, 별도의 닉네임 조회 API나 저장 공간을 만들지 않습니다.

예: 닉네임이 `학습자`라면 인사말은 `학습자님, 차곡차곡 쌓이고 있어요`, 왼쪽 계정명은 `학습자`, 아바타는 `학`으로 표시합니다.

이번 범위에서 공부 기록 24개·남은 할 일 4개·미해결 오류 2개, 공부 기록 목록, 날짜와 할 일은 계속 예시 데이터입니다. 할 일 체크는 화면 안에서만 동작합니다. 화면의 예시 데이터 안내를 유지하여 실제 계정의 공부 기록으로 오해하지 않게 합니다.

## 2. 현재 코드에서 확인한 사실

| 파일 | 현재 동작 |
| --- | --- |
| `frontend/src/App.jsx` | `/dashboard`는 인증 없이 렌더링됩니다. 나머지 화면만 `ExistingAppRoutes` 안의 `AuthProvider`를 사용합니다. `Protected`는 비로그인 사용자를 `/login`으로 보냅니다. |
| `frontend/src/auth/AuthContext.jsx` | `GET /api/accounts/session`으로 로그인 상태를 읽고 `user`를 제공합니다. 로그인과 닉네임 변경 응답도 같은 상태에 반영합니다. 로딩·오류·다시 연결 화면이 이미 있습니다. |
| `frontend/src/api/accounts.js` | `readSession()`과 `changeNickname()` 등 기존 API 호출이 있습니다. 진행 중인 세션 조회를 공유하는 처리도 있습니다. |
| `backend/app/accounts/router.py` | 세션 응답에 `user.nickname`이 포함됩니다. 새 API는 필요하지 않습니다. |
| `frontend/src/pages/dashboard/DashboardPage.jsx` | 인사말의 `이월님`, 계정명의 `이월`, 아바타의 `이`가 고정돼 있습니다. |
| `frontend/src/pages/accounts/LoginPage.jsx` | 로그인 성공 시 기존 홈 `/`로 이동합니다. |
| `frontend/src/tests/DashboardPage.test.jsx` | 현재는 인증·백엔드 요청 없이 예시 화면을 여는 것이 정상이라는 테스트가 있습니다. 연동 후 기준으로 바꿔야 합니다. |

## 3. 권장 동작

현재 예시 대시보드는 비로그인 상태에서도 열 수 있지만, 이번 연동부터 로그인한 사용자의 화면으로 전환하는 안을 권장합니다. 기존 PRD·SPEC의 개인 화면 접근 규칙과도 맞습니다. 아래는 이 안을 기준으로 한 계획이며 아직 적용하지 않았습니다.

| 상태 | 표시와 이동 |
| --- | --- |
| 로그인 상태 확인 중 | 기존 `AuthProvider`의 로딩 안내를 표시합니다. 예시 이름을 먼저 보여주지 않습니다. |
| 로그인 사용자 확인 성공 | 서버에서 받은 닉네임을 세 위치에 표시합니다. |
| 비로그인 또는 세션 만료 상태에서 새로고침 | 사용자 없음이 확인된 뒤 기존 `Protected`가 `/login`으로 이동시킵니다. |
| API·DB·네트워크 오류 | 기존 오류 안내와 다시 연결 버튼을 표시합니다. 비로그인으로 단정하거나 예시 이름으로 대체하지 않습니다. |
| 계정 설정에서 닉네임 변경 후 돌아옴 | 공유된 인증 상태의 변경된 닉네임을 표시합니다. |
| 대시보드 새로고침 | 세션을 다시 확인해 서버의 현재 닉네임을 표시합니다. 할 일 예시 체크는 초기화됩니다. |

가만히 열어 둔 페이지에서 세션 만료나 다른 탭의 닉네임 변경을 즉시 감지하는 기능은 이번에 추가하지 않습니다. 새로고침이나 기존 인증 조회가 이루어지는 시점에 서버 상태를 반영합니다.

로그인 성공 후 기존 `/` 이동은 유지합니다. 사용자는 로그인 후 `/dashboard`를 열어 확인합니다. 로그인 전 주소로 자동 복귀하거나 기존 홈을 대시보드로 교체하는 작업은 포함하지 않습니다.

## 4. 개발 순서

### 1단계: 기존 상태와 테스트 기준 확인

- 관련 파일과 진행 중인 사용자 변경을 다시 확인합니다.
- 기존 프론트엔드 테스트를 실행해 시작 시점의 결과를 확인합니다.
- 실서버 확인에 사용할 회원가입·로그인이 가능한지 확인합니다. 비밀번호, 쿠키와 DB 연결 문자열은 출력하지 않습니다.

### 2단계: 인증 상태를 모든 관련 화면에서 한 번만 공유

- `AppRoutes`에서 전체 경로를 하나의 `AuthProvider`로 감쌉니다.
- `ExistingAppRoutes` 안의 중복 제공자는 제거하고 기존 `Layout`과 내부 경로를 유지합니다.
- `/dashboard`에도 기존 `Protected`를 적용합니다.
- 대시보드에는 기존 일반 화면의 헤더·푸터를 덧씌우지 않습니다. 기존 Figma 사이드바와 레이아웃을 유지합니다.
- 대시보드와 계정 설정 사이에서 같은 로그인 상태가 유지되도록 합니다.

확인 기준: 제공자가 중첩되지 않고, `/login`, `/signup`, `/`, `/settings`가 기존 방식으로 동작합니다. 세션 조회를 대시보드에서 별도로 중복 호출하지 않습니다.

### 3단계: 닉네임 표시 연결

- `DashboardPage`에서 기존 `useAuth()`의 `user.nickname`을 읽습니다.
- 인사말, 왼쪽 계정명, 아바타 첫 글자의 고정 문자열을 교체합니다.
- 닉네임을 별도 로컬 상태나 localStorage에 복사하지 않습니다. 기존 인증 상태를 그대로 사용합니다.
- 닉네임은 일반 React 텍스트로 표시합니다. 임의 HTML로 삽입하지 않습니다.
- 이름이 없거나 조회에 실패했다고 `이월`로 돌아가지 않습니다. 표시 전 상태 구분은 기존 인증 처리에서 맡습니다.

확인 기준: 다른 닉네임으로 로그인하면 세 위치가 모두 해당 사용자의 이름으로 바뀝니다.

### 4단계: 긴 닉네임의 배치 확인

- 기존 허용 범위인 2~20자 닉네임으로 확인합니다.
- 인사말은 사용 가능한 너비에서 자연스럽게 줄바꿈하도록 합니다.
- 왼쪽 계정명은 좁은 공간에서 말줄임할 수 있게 하되 전체 이름은 접근 가능한 텍스트와 보조 표시로 확인할 수 있게 합니다.
- 필요한 경우에만 `DashboardPage.module.css`의 닉네임 관련 규칙을 보완합니다. 공통 CSS, 버튼 색상·크기와 다른 카드는 바꾸지 않습니다.

확인 기준: 데스크톱과 360px 화면에서 긴 닉네임 때문에 버튼이 겹치거나 가로 스크롤이 생기지 않습니다.

### 5단계: 자동 테스트와 빌드

- 기존 대시보드 테스트의 ‘인증·백엔드 요청 없음’ 전제는 새 로그인 기준으로 교체합니다. 이후에는 세션 조회가 필요하지만 대시보드의 별도 추가 조회나 데이터 변경 요청은 없어야 합니다.
- 테스트에서는 API를 가짜 응답으로 대체합니다. 실제 Supabase에 계정이나 데이터를 만들지 않습니다.
- 기존 회원가입·로그인·닉네임 변경 테스트와 대시보드의 할 일 체크·초기화 테스트를 함께 확인합니다.
- `frontend`에서 실행합니다.

```powershell
npm.cmd run test -- --run
npm.cmd run build
```

### 6단계: 브라우저 확인과 작업 기록

- 로그인한 계정으로 `/dashboard`를 열어 닉네임 세 곳을 확인합니다.
- 계정 설정에서 닉네임을 바꾸고 대시보드로 돌아온 뒤 변경된 이름을 확인합니다. 다시 돌아오는 경로는 기존 기능에 새 메뉴를 추가하지 않고 브라우저 이동이나 직접 주소 입력을 사용해 확인합니다.
- 새로고침 후에도 서버의 닉네임을 표시하는지 확인합니다.
- 비로그인 브라우저와 연결 실패 상황에서 정한 안내가 나오는지 확인합니다.
- Chrome 데스크톱·360px 크기를 확인하고 다른 브라우저·실제 휴대폰 등 확인하지 못한 범위를 구분합니다.
- `docs/setup.md`와 `docs/plan.md`에 바뀐 접근 조건, 완료 사항과 남은 일을 기록합니다. commit·push는 별도 요청이 있을 때만 합니다.

## 5. 테스트 시나리오

| 항목 | 기대 결과 |
| --- | --- |
| 사용자 A의 로그인 세션 | 인사말·계정명·아바타가 A의 닉네임을 표시 |
| 사용자 B의 별도 세션 | A의 이름이 남지 않고 B의 이름을 표시 |
| 세션 응답 대기 | 기존 로딩 안내만 표시하고 예시 이름이나 조기 로그인 이동이 없음 |
| 세션 응답의 사용자가 없음 | `/login`으로 이동하고 대시보드는 표시하지 않음 |
| 세션 조회 실패 후 재시도 | 오류와 재시도를 표시하고, 성공한 응답으로 회복 |
| 닉네임 변경 성공 후 대시보드 이동 | 변경된 이름 표시. 제공자 재생성으로 오래된 이름을 복원하지 않음 |
| 닉네임 변경 실패 | 기존 정상 닉네임 유지 |
| 새로고침 | 서버 세션의 현재 닉네임을 다시 표시 |
| 2자·20자 및 한글·영문·숫자 닉네임 | 이름과 아바타가 정상 표시되고 좁은 화면에서도 배치 유지 |
| 할 일 체크·해제 | 예시 개수와 완료율의 기존 동작 유지. 저장 요청 없음 |
| 기존 가입·로그인·홈·계정 설정 | 기존 이동·권한·입력 처리가 유지됨 |

## 6. 예상 변경 파일과 변경하지 않을 대상

| 파일 | 예상 변경 |
| --- | --- |
| `frontend/src/App.jsx` | 공통 `AuthProvider` 배치와 `/dashboard` 로그인 보호 |
| `frontend/src/pages/dashboard/DashboardPage.jsx` | 닉네임 세 곳을 `useAuth()`의 사용자 정보로 연결 |
| `frontend/src/pages/dashboard/DashboardPage.module.css` | 필요한 경우에만 긴 이름 표시 보완 |
| `frontend/src/tests/DashboardPage.test.jsx` | 인증 상태·닉네임·오류·기존 체크 기능 테스트 |
| `frontend/src/tests/accounts/AuthFlows.test.jsx` | 제공자 공유와 닉네임 변경 후 화면 전환에 대한 회귀 확인 |

기존 `AuthContext`·API 호출 모듈·로그인 성공 후 이동 처리는 재사용합니다. 현재 확인한 코드 기준으로는 백엔드 API, DB 테이블, Alembic, `.env`, Figma 디자인, 패키지 설치 변경이 필요하지 않습니다.

## 7. 완료 기준과 사용자의 준비

- 로그인한 사용자의 닉네임이 세 위치에서 일관되게 표시됩니다.
- 비로그인·로딩·조회 실패를 구분하고 예시 이름을 실제 이름 대신 보여주지 않습니다.
- 닉네임 변경 후 이동과 새로고침에서 현재 닉네임을 표시합니다.
- 예시 기록·할 일 동작과 기존 화면이 유지됩니다.
- 프론트엔드 테스트·빌드와 범위 내 브라우저 확인을 통과합니다.
- 사용자가 개발을 위해 새 API 키나 DB 설정을 추가할 필요는 없습니다. 수동 확인에는 기존 백엔드·DB 연결, 테이블 준비와 로그인 가능한 계정이 필요합니다. 현재 실제 DB 연결 상태는 이번 계획 작업에서 확인하지 않았습니다.

2026-10-23 계획 작성 단계에서는 파일과 흐름만 확인하고 문서를 작성했습니다. 이후의 구현·검증 결과는 위의 SDD와 진행 기록을 참고합니다.
